PART 1 -- NEW FEATURE: Manual/Test "Hold-to-run" buttons
================================================================================

WHAT IT DOES
  Press-and-hold buttons on the website's Manual/Test tab, one per relay
  target (same 9 targets as the existing Timed Pulses dropdown: transfer,
  colA/B/C, mixer, nutA/B/C, phUp, phDn). Energises the relay only while held;
  stops the instant you release, lose connection, switch away, or the tab goes
  hidden. This SITS ALONGSIDE the existing Timed Pulses feature -- both exist,
  neither replaced the other, per your explicit instruction.

  Mechanically it is the website's equivalent of the LCD Testing screen's own
  physical dead-man button, reusing ESP2's EXISTING TEST,HOLD / TEST,RELEASE
  protocol untouched. ESP2 firmware needed ZERO changes.

HOW IT WORKS END TO END
  1. Website writes {seq, bit, want} to Firebase at irrigation/testHold on
     mousedown/touchstart (want:true) and mouseup/touchend/etc (want:false),
     refreshing every 1.2s while held.
  2. ESP1's new firebasePollTestHold() polls that node every 3s (same cadence
     as every other command poll), and when it sees a genuinely new request it
     arms ESP2 (TEST,ENTER), then streams TEST,HOLD,<row> every 150ms -- well
     inside ESP2's own 400ms dead-man -- for as long as the website keeps
     refreshing want:true.
  3. If the website goes silent for more than 8 seconds (TEST_HOLD_BROWSER_
     TIMEOUT_MS), ESP1 releases on its own. Either way, ESP2's own 400ms
     hardware dead-man is the actual physical safety backstop, exactly as it
     already is for the LCD's own Testing screen and for Timed Pulses.
  4. Corrosive targets (pH Up/Down) need one confirm() dialog first, which
     "arms" that button for 8 seconds -- a plain tap does nothing; you must
     confirm, then press-and-hold within that window.

BUG I FOUND AND FIXED WHILE BUILDING THIS (before you ever saw it)
  My first draft set the "browser vanished" timeout to 3000ms -- identical to
  ESP1's own Firebase poll interval (FIREBASE_COMMAND_POLL_MS). That would have
  falsely released a still-held button on nothing worse than one slow poll
  cycle. Fixed by raising it to 8000ms, comfortably clearing 2+ poll cycles.

PART 2 -- FIX: Manual/Test "Proceed" stuck when ESP1 snapshot is stale
================================================================================

THE BUG YOU REPORTED
  "When the website is in Waiting for a current ESP1 snapshot, I can't access
  Manual/Test -- it's stuck and the Proceed button is unclickable."

ROOT CAUSE
  Proceed was disabled until ESP1's webManual state actually reached "held" --
  but ESP1 can only grant that once it is alive. With no snapshot at all,
  state stays "idle" forever, so Proceed was permanently disabled. There was
  no way in.

THE FIX (matches the design you confirmed)
  - Proceed now only checks that your account is approved -- it always reveals
    the Manual/Test screen. It no longer waits for ESP1 to grant anything.
  - Every individual test button (Timed Pulses, hold-to-run, exercise, sweep,
    etc.) stays disabled via the EXISTING freshness/approval check
    (syncControlAvailability()) until ESP1 is genuinely connected -- so you
    can get into the tab, but nothing fires blind.
  - A banner inside the controls area now reads:
      Stale:      "ESP1 appears offline -- Snapshot received Xm ago. Requests
                   are queued but nothing runs until it reconnects."
      Reconnected: "Direct hardware control -- this tab drives the hardware
                   directly." (the same warning re-surfaced as a reminder)

A SECOND BUG I FOUND WHILE FIXING THIS ONE
  The existing "kick the operator back out" logic (for when ESP1 revokes or
  refuses a hold) was written as "if state is not held, back out" -- which
  used to be safe only because you could never get IN except via "held" in
  the first place. Now that Proceed lets you in with a stale/idle state, that
  same line would have instantly un-proceeded you the moment you clicked
  Proceed on a stale snapshot -- defeating the entire fix. Narrowed it to only
  fire on an ACTUAL revoke/refuse (a hold that was granted and then taken
  back), not on "never granted yet."

PART 3 -- 5 FIXES FROM THE PRIOR DEEP-SCAN (NOW CLOSED OUT)
================================================================================

1. [HIGH] writeManualHold() release-gate bug
   Before: releasing Manual/Test (want=false) was gated behind isApprovedUser()
   -- the SAME check that gates acquiring it -- directly contradicting the
   function's own comment ("releasing must always go through"). If an operator
   restricted/blocked an account WHILE it held Manual/Test, that account's own
   release write silently failed, leaving the relay held until ESP1's 60s
   lease timed it out on its own instead of releasing immediately.
   Fixed client-side (release now only requires being signed in) AND
   server-side (firebase-rules.json's irrigation/manual .write now also
   allows the write when want===false, regardless of approval status).

2. [MEDIUM] Force Run's doseMl had no server-side validator
   liters/delaySeconds/targetN/P/K/PH all had range validators; doseMl{A,B,C}
   (the per-nutrient mL amounts) did not -- client capped it at 500mL each,
   but nothing stopped a tampered/replayed request server-side. Added
   matching 0-500 validators for doseMl/A, doseMl/B, doseMl/C.

3. [MINOR] canAccessPrivilegedTabs() didn't re-check approval
   hasTempAccess() only checks the grant's timestamp, not current standing --
   restricting/blocking an account mid-grant left it privileged (could still
   see Manual/Test + System) until the grant's own clock ran out, up to an
   hour later. Fixed: now requires hasTempAccess() AND isApprovedUser()
   together.

4. [MINOR] Restrict/Block didn't clear a live tempAccessUntil grant
   If an account was restricted or blocked while still holding an
   unexpired temp-access grant, re-approving it before that grant's own
   clock ran out silently handed privileged access straight back with no
   fresh grant from an operator. Fixed: any status change away from
   "approved" (reject/block/restrict) now clears tempAccessUntil in the
   same write.

5. [OPERATIONAL] Vercel ALLOWED_ORIGIN
   Checked via `vercel env ls` against the delete-user-api project: it IS
   set in Production. No action needed -- closing this out, not a code bug.
