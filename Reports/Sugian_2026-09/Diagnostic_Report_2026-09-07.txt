PROBLEM 1 -- Force Run rejected: "someone is using the LCD"
================================================================================

ROOT CAUSE / MECHANISM (not a bug -- working as designed):
ESP1 gates every new remote or automatic actuation (FORCE_RUN, TEST_PULSE, RUN_PUMP_TEST, the
scheduler controlTick(), and the pump-exercise exerciseTick()) behind a 7-condition "safely idle"
check. The literal string "someone is using the LCD" is the last, catch-all branch of that check,
reached only when nothing more specific applies:

  ESP1/src/main.cpp:6174-6188 (FORCE_RUN handler, firebaseCommandTick())
  if (sysState != IDLE_STATE || uiMode != UI_DATA || wo.active || pendingRun.active ||
      pendingExercise.active || esp2Held || fbRemoteExerciseId[0] ||
      actuationsDisabled || webManualHeld()) {
    const char *why = (sysState != IDLE_STATE || wo.active || pendingRun.active) ? "a run is in progress"
                     : esp2Held ? "a fault is held"
                     : (pendingExercise.active || fbRemoteExerciseId[0]) ? "a test is already running"
                     : actuationsDisabled ? "actuations are disabled"
                     : webManualHeld() ? "the Manual/Test tab has direct control"
                     : "someone is using the LCD";
    firebaseQueueStatus(c.id, "rejected", why);

(Same literal string is duplicated at 4 other call sites: :3327, :6313, :6491, :7922 -- no shared
helper function.)

The variable is uiMode (ESP1/src/main.cpp:1120-1121, enum {UI_DATA, UI_MENU, UI_EDIT, UI_TEST,
UI_CAL, UI_DIAG}), set away from UI_DATA by opening Settings/Testing/Calibration/Sensor Diag/any
field editor on the physical LCD. This is explicitly a DIFFERENT mechanism from the "Lock Screen"
feature (lcdLocked, :1361) -- the code comment is explicit:

  ESP1/src/main.cpp:1358-1360:
  /* ---- LCD lock (Part D: manual stranger-lock, independent of uiMode) -------- *
   * lcdLocked gates ONLY the buttons + LCD render -- automation still runs because
   * controlTick/exerciseTick gate on uiMode (which stays UI_DATA while locked).    */

So turning on Lock Screen does NOT cause this rejection; it only fires when a person has genuinely
opened a menu.

    (:8323-8333) auto-returns to UI_DATA after 5 minutes of no button press -- explicitly EXCEPT

PROBLEM 2 -- Column settings rejected: "mode must be AUTO or IRRIGATION_ONLY"
================================================================================

ROOT CAUSE -- A GENUINE FIRMWARE BUG, FULLY IDENTIFIED:

  ESP1/src/main.cpp:727:  char  colMode[14];    // "AUTO" | "IRRIGATION_ONLY" ("" = absent)

The literal string "IRRIGATION_ONLY" is 15 characters + a null terminator = 16 bytes. The buffer
is only 14 bytes. The copy that fills it uses the safe, truncating strlcpy (no memory corruption --
just silent data loss):

  ESP1/src/main.cpp:6086: strlcpy(c.colMode, req["payload"]["mode"] | "", sizeof(c.colMode));

strlcpy with sizeof(c.colMode)==14 copies at most 13 characters, so "IRRIGATION_ONLY" becomes
"IRRIGATION_ON" (13 chars) inside c.colMode. That truncated string then fails BOTH comparisons in
the validator:

  ESP1/src/main.cpp:6374-6378:
  if (c.colMode[0]) {
    if      (!strcmp(c.colMode, "AUTO"))            { newMode = MODE_AUTO;            setMode = true; }
    else if (!strcmp(c.colMode, "IRRIGATION_ONLY")) { newMode = MODE_IRRIGATION_ONLY; setMode = true; }
    else { firebaseQueueStatus(c.id, "rejected", "mode must be AUTO or IRRIGATION_ONLY"); continue; }
  }

-> falls through to the else -> THE EXACT REJECTION THE USER SAW.

SCOPE OF IMPACT: Only "Irrigation only" is affected (15 chars, truncates). "AUTO" (4 chars) fits
easily and works. "(unchanged)" (empty string) also works correctly -- see below. This is 100%
reproducible, not intermittent: selecting "Irrigation only" for any column, every time, will always
be rejected.

THE WEBSITE IS COMPLETELY INNOCENT HERE -- AND THE "(unchanged)" DESIGN IS ALREADY CORRECT.
Confirmed on both ends:
  - Website (script.js:713-717,1364-1365): <option value="">(unchanged)</option>, and
    "if (mode) payload.mode = mode;" -- an empty string is falsy, so the mode key is OMITTED
    entirely from the payload when "(unchanged)" is selected. Author's own comment: "the firmware
    treats absent fields as 'leave unchanged,' so a partial edit cannot clobber the rest of the
    column's configuration" (script.js:1361-1362).
  - Firmware (ESP1/src/main.cpp:6086,6374): an absent JSON mode key defaults to "" via
    ArduinoJson's | "" operator, and "if (c.colMode[0])" correctly skips validation entirely for
    an empty string -- mode is left untouched, and the rest of the command (other fields) can still
    succeed. This is a clean, working, two-pass validate-then-apply design
    (ESP1/src/main.cpp:6361-6363,6407-6408) that explicitly guards against a bad field leaving
    earlier fields "applied-live-but-unsaved."

So the user's working theory (that the website might be sending an invalid sentinel for
"(unchanged)") is NOT what's happening -- that path already works. The actual bug is an unrelated,
narrow buffer-size mistake that only bites the real, valid "IRRIGATION_ONLY" value.

ANSWERS TO THE NUMBERED SUB-QUESTIONS:
 1. Dropdown options: exactly ""/"AUTO"/"IRRIGATION_ONLY" (script.js:713-717) -- correct.
 2. Website validation: none beyond the <select>'s own constrained value set, plus a "must change
    at least one field" client-side guard (script.js:1398) -- no bug here.
 3. Firebase structure: {col, mode?, enabled?, schedMode?, winStart?, winEnd?, targetN/P/K/PH?} --
    matches firmware's expectations field-for-field.
 4. ESP1 parser: firebaseCommandTick()'s SET_COLUMN branch, ESP1/src/main.cpp:6354-6431.
 5. Exact accepted values: "AUTO" or "IRRIGATION_ONLY", case-sensitive exact match only.
 6. "(unchanged)" means: don't touch this column's stored mode; only fields actually supplied get
    changed.
 7. Yes, and it already IS represented by omission (empty string / absent JSON key) -- this part
    is already correct on both website and firmware.
 8. No -- confirmed the website already omits the key correctly.
 9. No -- the fix cannot be made in Website/script.js at all; the defect is entirely inside ESP1's
    fixed-size C buffer.
10. Firebase rules: not involved -- no .validate on mode's shape in irrigation/commands beyond
    source/status, so this is purely an ESP1-internal string-handling bug.
11. Yes, firmware change is required -- see fix below.

CLASSIFICATION: Firmware (ESP1). P2 -- functional bug, not safety-critical (no relay energizes
incorrectly; it just prevents saving a legitimate configuration choice).
FIXABLE WITHOUT FLASHING: No.
RECOMMENDED FIX: Widen the buffer, e.g. "char colMode[20];" (ESP1/src/main.cpp:727) -- the smallest
possible safe change (16 bytes needed minimum; 20 leaves headroom for a possible future value
without ever repeating this class of bug). No other line needs to change -- strlcpy's
sizeof(c.colMode) argument auto-adjusts. Does not weaken validation -- the strcmp checks stay
exactly as strict; this only fixes truncation upstream of them, exactly matching the user's
instruction not to weaken ESP1 validation.
SAFETY IMPACT: None -- pure data-integrity fix, no control-path/safety-interlock changes.

PROBLEM 4 -- Transfer pump flow test: "completed - NO FLOW - 0 pulses, check pump"
================================================================================

WHAT "completed" ACTUALLY MEANS (this is the crux, and it is by design, not a bug):

  ESP1/src/main.cpp:8796-8799 (pulseTick, PU_REPORT phase):
    // Waiting on ESP2's TEST,FLOW answer so the result can say whether fluid actually moved --
    if (puFlowSeen || millis() - puReportMs > PULSE_REPORT_WAIT_MS) pulseFinish(true, "pulse complete");

ok=true ("completed") fires purely because the timed pulse FINISHED WITHOUT BEING ABORTED by a
fault/lockout/menu interruption -- it says nothing about flow yet. The flow verdict is computed
SEPARATELY, immediately after, inside pulseFinish():

  ESP1/src/main.cpp:8748-8757:
  if (ok) {
    if (k <= 0.0f)        detail += "; no flow sensor on this output";
    else if (!sawFlow)    detail += "; no flow report from ESP2";
    else {
      ...
      detail += pulses ? ("; FLOW OK " + String(pulses) + " pulses ~" + vol)
                       : String("; NO FLOW - 0 pulses, check pump, line or sensor");
    }
  }

The exact string the user saw ("NO FLOW - 0 pulses, check pump...") only appears in the branch
where ESP2 DID reply with a valid pulse count (sawFlow==true) and that count was exactly zero.
This rules out a communications glitch (the "no flow report from ESP2" branch is a distinct,
different message) and rules out a missing/zero calibration K-factor (the "no flow sensor on this
output" branch is also distinct). This is a clean, unambiguous "ESP2 counted zero pulses on GPIO26
during the pump-run window" result.

BATTERY VOLTAGE (commissioning fact, not a numbered problem, but explicitly requested)
================================================================================

Confirmed: ESP1 does have battery voltage code (readBatteryAdc(), ESP1/src/main.cpp:4872-4887),
reading GPIO35 through a calibration polynomial (calBattV). Two things compound the "must not
pretend a voltage exists" risk:

1. NO INSTALLED/CALIBRATED CHECK GATES THE PUBLISHED NUMBER. The default (uncalibrated) polynomial
   is calBattV = {1, {0.0, 1.0, 0.0, 0.0}} (:1032) -- i.e. battV = raw_adc/4095 when never
   calibrated. A flag battCalLoaded (:1034) does exist and correctly tracks whether real NVS
   calibration was ever loaded -- but it is ONLY used for a boot-time serial print (:4828); it is
   NEVER consulted before publishing battV to Firebase/LCD. With the sensor not physically
   installed, GPIO35 will float or read some arbitrary value, and the firmware will still compute
   and confidently display SOME number rather than "Unavailable."

2. THE WEBSITE'S DIAGNOSTICS "Battery sensor: OK/Not OK" FLAG DOES NOT REFLECT THE VOLTAGE PATH AT
   ALL. Tracing it precisely: dpe["batterySensorOk"] = t.acsOk_ (ESP1/src/main.cpp:5689) <-
   telem.acsOk_ = acsOk (:5173) <- acsOk = acsReadVolts(vAdc) inside readBatteryAdc() -- this is the
   BATTERY CURRENT sensor (an ACS758 via a separate ADS1115 I2C ADC, which itself replaced an
   earlier dead opto-current path -- code comment: "Current now comes from the ACS758 via the
   ADS1115, NOT the opto ADC on GPIO34 (which read 0.00 A on every sample for 16 days)"). So
   "Battery sensor: OK" can show OK purely because the CURRENT chain responded, while saying
   nothing about whether the displayed VOLTAGE number is real or a meaningless floating-pin
   artifact.

DIRECT ANSWERS
================================================================================

A. CAN "someone is using the LCD" BE IMPROVED WITHOUT FIRMWARE?
Yes for polish, but nothing is actually broken. The current message is already a direct,
human-readable string from firmware (not a vague code), and it already self-clears within 5 minutes
automatically or immediately on BACK/reboot. Recommend a website-only help-text addition; a richer
message (naming which menu) would need a small, optional, low-risk firmware telemetry addition.

B. CAN THE COLUMN SETTINGS REJECTION BE FIXED WITHOUT FIRMWARE?
No. The website is already sending and handling everything correctly. The bug is a 14-byte C buffer
in ESP1 that truncates the literal string "IRRIGATION_ONLY" before it's compared -- this can only be
fixed by widening that buffer and reflashing ESP1.

C. CAN INDIVIDUAL RELAY BUTTONS BE ADDED WITHOUT FIRMWARE?
Mostly moot -- Transfer, Booster, Mixer, and the 3 column-push combos are ALREADY exposed on the
Manual/Test page, dispatched through commands ESP1 already implements, over a Firebase path whose
rules already permit them. No new relay buttons are recommended for the Reservoir Valve or other
bare valves -- this was deliberately excluded by the original design because there's no way to
confirm a valve's position afterward, and adding it would reintroduce a dead-heading risk the
current design specifically avoids.

D. DOES THE 0-PULSE TRANSFER TEST CONFIRM THE PHYSICAL FLOW PROBLEM?
Yes, with high confidence. The exact response text only occurs when ESP2 successfully replied with
a genuine zero pulse count -- ruling out a UART/communication failure and ruling out a
missing/invalid calibration factor as explanations. The valve is confirmed to already be opened
correctly by this test (it uses the Fill combo, not the bare pump relay), ruling out "closed valve"
as the cause. This matches a previously-documented (2026-08-07), independently-confirmed hardware
flow fault on this same subsystem.

E. WHAT SHOULD BE PHYSICALLY INSPECTED NEXT?
In order of likelihood, reusing (and re-verifying, since firmware changed but hardware did not) the
checklist from the prior diagnostic report:
  1. The reservoir->mix (transfer/fill) flow sensor itself -- is it connected, correctly oriented
     (flow-direction arrow), and genuinely in the water path?
  2. The transfer pump -- does it audibly/physically spin when the test runs? (Listen during a
     repeat test.)
  3. Reservoir level and inlet -- is there actually water available to draw from?
  4. The PCF8575 relay outputs for OUT_RES_VALVE (bit 0) and OUT_TRANSFER (bit 6) -- confirm the
     physical relays click during the test.
  5. Air-lock or blockage in the pump/pipe run.
  6. AC power path -- confirm OUT_INVERTER engages and check PZEM logs for a concurrent PWR_FAIL/
     overcurrent alongside the flow result.
Also recommended: re-run the Manual/Test pulse at 10-15 SECONDS (not 5) to match/exceed ESP2's own
10-second production FLOW_TIMEOUT_MS, for a maximally comparable, conclusive result.
