MAJOR REVISION -- COLUMN MODE: WHAT WAS FOUND, WHAT'S BEING BUILT
---------------------------------------------------------------------
INVESTIGATED FRESH THIS ROUND: the current "Zone Profiles" tab already shows ALL 3 PHYSICAL COLUMNS
SIMULTANEOUSLY as separate always-visible cards (A, B, C -- confirmed exactly 3 columns exist in
firmware, tagged A/B/C). Column-enabled state currently defaults to Enabled, Enabled, Disabled --
COLUMN C IS DISABLED BY DEFAULT TODAY. Each card already has live sensor readings, a crop/stage
planning picker (website-only, doesn't touch ESP1), and a "Firmware settings" form
(mode/enabled/schedule/window/targets) that sends to the existing column-settings command.

THE REAL GAP, PRECISELY IDENTIFIED: every field in that firmware-settings form defaults to either
"(unchanged)" or blank -- NONE OF THEM DISPLAY THE COLUMN'S ACTUAL CURRENT VALUE. Confirmed by
tracing the telemetry-publishing code directly: the column's real mode / enabled-flag / schedule-mode
/ window start-end / N-P-K-pH targets are NEVER referenced anywhere in the function that builds the
live telemetry snapshot -- only per-column SENSOR readings are published today. This is a write-only
form, not a status display, which is the actual root of what your request is pointing at.

DESIGN DECISION ON THE REQUESTED "[Column A dropdown]" SELECTOR -- stated explicitly so it can be
overridden if this reading is wrong: your requirement #8 ("clearly see which columns are currently
active/enabled") and requirement #1 ("see all available columns") are already served BETTER by the
existing simultaneous-3-cards layout than a single dropdown that hides the other two columns would
be -- a hide-others selector would make it HARDER, not easier, to see at a glance which columns are
active. Rather than replace the card layout with a dropdown, THE PLAN IS TO KEEP the
three-cards-at-once structure (it already IS "select which column to configure" -- you edit the card
for the column you want) AND FIX THE ACTUAL GAP: add a live "Current: ..." status readout to each
card, sourced from real ESP1 state, so requirements #3, #8, and the source-of-truth requirement are
properly met without inventing a second, competing UI paradigm or a website-only "active column"
concept that doesn't correspond to anything in firmware. "Selected for editing" stays naturally
distinct from "enabled for operation" because Enabled is its own visible field/toggle in each card --
not something merely looking at a card changes.

WHAT THIS REQUIRES:
1. New ESP1 telemetry (additive, read-only, no new command): publish each column's actual mode,
   enabled state, schedule mode, resolved window start/end, and N/P/K/pH targets into the live
   telemetry snapshot. All values ESP1 already holds in memory -- nothing new is computed, only
   exposed.
2. Website: each zone card gets a "Current configuration" readout (Mode, Enabled, Schedule/Window,
   Targets) rendered from that new telemetry, positioned above the existing edit form, so the
   operator sees real state before deciding what to send -- plus the new Preset dropdown (below).
   After a column-settings send succeeds, the next telemetry refresh naturally updates this readout,
   satisfying "after a setting is sent, read/display the actual resulting state."
3. Exact valid modes, read from source, not assumed: there are exactly two real mode values, AUTO and
   IRRIGATION_ONLY. The LCD's apparent "3rd state" is not a mode value at all -- it is the SEPARATE
   column-enabled flag (OFF = disabled, independent of mode). The website's existing dropdown
   (AUTO / IRRIGATION_ONLY / blank-for-unchanged) already matches this exactly -- confirmed correct,
   not being changed.
4. Exact valid columns, read from source, not assumed: exactly 3, fixed in firmware -- A, B, C --
   matching the website's existing zone ids one-to-one. There is no firmware concept of
   adding/removing/renaming a column beyond these 3 (a 4th zone would require new firmware/hardware,
   out of scope).
5. Preset, reusing the existing column-settings command with one additive field (unchanged from the
   prior round's plan): add one new optional field to that command's payload; if supplied, resolve it
   server-side against firmware's REAL 4-entry preset table (PECHAY, TOMATO_S1, TOMATO_S2, TOMATO_S3),
   applying N/P/K/pH exactly like the existing text-message preset command already does; reject
   unknown names. This stays entirely separate from the website's own 7-crop database / "Fill targets
   from crop profile" feature, which is untouched and not replaced.

NO CONFLICT WITH FIRMWARE ARCHITECTURE OR SAFETY WAS FOUND for this design -- reporting as required,
this is the one place a genuine design judgment call was made (dropdown vs. cards), and it's flagged
above with reasoning rather than silently decided.


NEW APPROVED CHANGE -- FORCE RUN RACE FIX
----------------------------------------------
ROOT CAUSE, CONFIRMED PRECISELY: the Force Run arm-phase state is ALREADY a single shared
authoritative variable that both the LCD and the website/Firebase arm paths read and write -- there
are not two competing states needing unification, just one missing check. The Firebase Force Run
handler already refuses to arm a new run over an existing armed one, replying "rejected -- another
forced run is already armed." The LCD's own Force Run commit code has NO equivalent check -- it
unconditionally arms, silently overwriting a web-armed run's countdown and parameters, with no
rejection ever posted back to the dashboard.

THE FIX (small, surgical, additive): add the exact same guard to the top of the LCD's Force Run
commit code -- if a run is already armed or running, log it and show a clear local message instead of
overwriting. This makes both entry points consistently respect the one shared state that already
exists, rather than inventing a new one. The reverse direction (web silently overwriting a local arm)
is ALREADY safe today -- the Firebase handler already has this exact check -- confirmed only the LCD
side was missing it.

ON-SCREEN MESSAGE: implemented using the LCD's existing pattern for brief status feedback rather than
inventing a new UI subsystem -- exact rendering mechanics finalized against the live render function
during implementation, but the guard condition and the exact block point are already identified and
final.

NOT otherwise redesigning Force Run sequencing -- the arm/countdown/fire-time re-check mechanism,
delay bounds, and everything else about how a forced run actually executes stays untouched.
