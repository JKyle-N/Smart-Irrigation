PART 1 -- ESP1 (master controller)
================================================================================

1. [FIXED, HIGH] New hold-to-run polling function called core-1-only functions
   directly from core 0 (netTask) -- a genuine cross-core race
--------------------------------------------------------------------------------
`firebasePollTestHold()` runs entirely inside `netTask`, which is pinned to
core 0. It was calling `setState(TEST_MODE)`, `logEvent(...)`, and (via
`pulseFinish()`) `sendEsp2()` directly from there. `logEvent()` unconditionally
appends to the single global `String logBuf`, which core 1 mutates dozens of
times/sec elsewhere; ESP32 Arduino's `String` has no internal locking, and a
concatenation can trigger a heap `realloc`. Two FreeRTOS tasks on two physical
cores mutating the same String with no mutex is EXACTLY the bug class this same
file already found and fixed twice before (the fbAuthErrLog/fbPollErrLog
deferred-logging hand-off, whose own comments describe the identical failure
mode almost verbatim) -- this reintroduced it.
I independently confirmed this by tracing the call graph: `firebaseCommandTick()`
(which safely does the equivalent job for TEST_PULSE -- arming, setState,
logEvent) is called from loop() at main.cpp:1764, i.e. CORE 1, not from inside
netTask. `firebasePollTestHold()`, by contrast, did the network fetch AND the
state-mutating actions in one function, and I had placed its call site inside
netTask alongside firebasePollManual() -- an incomplete mirror of the pattern it
claimed to copy.
Concrete failure scenario: pressing a hold-to-run button on the dashboard could,
if the timing lined up with core 1's own routine logging, corrupt the heap
(possible crash/reboot) or interleave garbage bytes into an ESP2 UART frame in
flight at that instant.
FIX APPLIED: `firebasePollTestHold()` is now a pure scalar hand-off (mirrors
firebasePollManual()/webManualTick()'s own split exactly) -- it only ever writes
three plain scalars (`testHoldReqWant`, `testHoldReqBit[12]`, `testHoldReqFresh`)
and `testHoldLastFreshMs`. All the actual arm/release logic (the idle/safety
gate check, `esp2SetPower()`, `setState()`, `logEvent()`, `pulseFinish()`) moved
into `pulseTick()`, which already runs every loop() iteration on core 1 (same
call site as `testHoldTick()`). Rebuilt successfully after the change.

2. [SELF-CAUGHT, would have been HIGH] Buffer too small for the longest target
   string, while implementing fix #1
--------------------------------------------------------------------------------
The new hand-off scalar was first written as `char testHoldReqBit[8]`. The
longest target string is "transfer" -- 8 characters, needing 9 bytes with the
null terminator. `strncpy()` into an 8-byte buffer would have silently
truncated it to "transfe", which would never match `pulseRowForTarget()`'s
`strcmp(t, "transfer")` check -- every hold-to-run request for the transfer
pump would have silently failed to arm, with no error surfaced anywhere.
Caught and fixed before ever building: buffer sized to 12 bytes.

3. [FIXED, low] Hold-to-run events never reached the dashboard's diagnostics/
   event log
--------------------------------------------------------------------------------
`webWorthy()`'s allow-list for `type=="ACT"` recognized `"TEST|"`, `"PULSE|"`,
`"EXERCISE|"` prefixes but not the new feature's own `"TESTHOLD|..."` lines --
so arming, finishing, or aborting a web hold-to-run press was completely
invisible in the dashboard's Recent Events / diagnostics, unlike every other
remote-triggered action. No safety impact (ESP2's own dead-man is unaffected
either way) -- purely an operator-visibility gap.
FIX APPLIED: added `d.startsWith("TESTHOLD|")` to the same check that already
covers TEST|/PULSE|/EXERCISE|.

Verification of the five earlier-in-session fixes (SET_THRESH validation,
tsUpload() validity gating, WIFIPORTAL,STOP case-sensitivity, schedule
start/end wrap validation, restoreDefaults()'s fertGap default): all five
independently re-confirmed correct and unregressed, with exact file:line
citations in the full audit transcript.

ESP1 build after both fixes: SUCCESS. RAM 23.6% (77,304 B), Flash 41.2%
(1,296,881 B) -- matches the known-good reference (77,288 B / 1,296,885 B)
almost exactly; the tiny few-byte delta is the expected result of restructuring
a handful of lines, not a red flag.

PART 3 -- Website / Firebase / Vercel
================================================================================

1. [FIXED, medium] /irrigation/testHold's rule was missing the release
   carve-out /irrigation/manual already has
--------------------------------------------------------------------------------
writeTestHold()'s own comment in script.js explicitly says "releasing always
goes through regardless of tier, so a lost grant... can never leave a relay
stuck energised because the release write itself got refused" -- matching
/irrigation/manual's rule, which has exactly that carve-out
(`newData.child('want').val() === false || ...`). /irrigation/testHold's rule
had NO such branch: every write, including release (want:false), required the
operator/temp-access/subOperator check.
Concrete failure scenario: an operator withholds a Sub-operator grant (or a 1h
temp grant expires, or the account gets restricted/blocked) at the exact
moment that account is holding a hold-to-run button down. The release write is
now rejected server-side with PERMISSION_DENIED instead of succeeding -- the
Firebase-side `want` flag is left stuck true (though physical safety is still
independently backstopped by ESP2's hardware dead-man and ESP1's own 8s
browser-timeout, both unaffected by what's in Firebase).
FIX APPLIED: added the identical `want:false` carve-out to testHold's write
rule, mirroring /irrigation/manual exactly.

2. [FIXED, low] setManualTestArmed() had no privilege check of its own
--------------------------------------------------------------------------------
Every top-level function in this non-module script is implicitly reachable
from a browser console. This one function could flip #mtGate/#mtControls's
hidden state for ANY signed-in account (even pending/rejected/disabled), one
layer deeper than the tab-click-handler and Proceed-button checks already
built to close this exact class of gap. Impact was cosmetic only (every real
write underneath re-verifies privilege independently, client AND server-side).
FIX APPLIED: added the same canAccessPrivilegedTabs() guard at its own top.

3. [FIXED, low] Toast notifications could leak DOM nodes forever for a viewer
   with reduced-motion/animations disabled
--------------------------------------------------------------------------------
Removal depended entirely on a transitionend event, which never fires for an
effectively-zero-duration transition. activeToasts (the tracking Map) was
already cleaned up correctly either way -- this was a silent DOM leak, not a
functional one, but could accumulate over a long session.
FIX APPLIED: a 300ms fallback setTimeout races the transitionend listener;
whichever fires first removes the element, the other is a harmless no-op.

4. [FIXED, low] delete-user-api's cleanup used Promise.all instead of
   Promise.allSettled
--------------------------------------------------------------------------------
admin.auth().deleteUser() already commits before the three-node cleanup
(/users, /presence, /activity) runs. With Promise.all, one transient failure
among the three removes rejected the whole batch and reported a 500 "delete
failed" even though the Auth account was already gone -- and a retry's very
first line would then throw "no such user" before ever reaching cleanup again,
permanently orphaning whichever node didn't get removed the first time.
FIX APPLIED: switched to Promise.allSettled with per-path failure reporting
(logged server-side, and returned as a non-blocking `cleanupFailed` list in the
response) so a partial cleanup failure is visible instead of silently orphaning
data or being conflated with an actual delete failure.
