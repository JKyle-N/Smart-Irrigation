4. WHY A DIRECT WRITE FROM A NORMAL APPROVED (NON-OPERATOR) ACCOUNT IS NOW REJECTED
====================================================================
For a normal-approved account attempting to create a command of one of the six privileged types:
the outer clause `(root.child('users')...status... === 'approved' || auth.uid === OP1 || auth.uid
=== OP2)` still evaluates true (their status IS "approved"), and `!data.exists()`/`source`/`status`
all still pass exactly as before — but the NEW inner ternary now also has to pass: since
`newData.child('type').val()` matches one of the six privileged names, the ternary evaluates its
"then" branch, `(auth.uid === OP1 || auth.uid === OP2)` — which is FALSE for any UID that isn't one
of the two literal operator UIDs. The whole CREATE branch's AND-chain therefore evaluates to FALSE.
The ESP1 branch is also FALSE (their UID isn't ESP1's device UID either). With both OR-branches
false, Firebase's default-deny takes over and the write is rejected — regardless of whether the
request came through this website's own JavaScript or a hand-crafted request straight to the
Realtime Database REST/SDK using that same account's valid ID token. This is what makes it a real
server-side boundary rather than a UI convenience: the rejection happens in Google's own rules
engine, before the write ever reaches storage, with no dependency on this website's client code
running at all.
