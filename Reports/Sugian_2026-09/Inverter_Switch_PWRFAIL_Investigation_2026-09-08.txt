INVERTER SWITCH / RELAY / PWR_FAIL INVESTIGATION
=================================================

1-2. EXACT ESP2 INVERTER GPIO/PCF8575 OUTPUT
#define OUT_INVERTER 5 (ESP2/src/main.cpp:113) -- PCF8575 bit P5, comment: "inverter relay (AC
source)". This is an I2C-expander bit, not a raw ESP32 GPIO -- ESP2 never drives the inverter relay
through its own GPIO pins directly, only through the PCF8575 (same as every other actuator).

3. RELAY ON/OFF POLARITY -- confirmed exactly
  ESP2/src/main.cpp:569: void pcfOn(uint8_t bit)  { pcfWrite(pcfShadow & ~(1 << bit)); }  // clear bit = ON
  ESP2/src/main.cpp:570: void pcfOff(uint8_t bit) { pcfWrite(pcfShadow |  (1 << bit)); }  // set bit  = OFF
ACTIVE-LOW: a relay is energized ("ON") when its PCF8575 bit is driven LOW (cleared), and
de-energized ("OFF") when driven HIGH (set). Applies uniformly to every relay including
OUT_INVERTER -- nothing inverter-specific about its polarity.

4. EVERY PLACE OUT_INVERTER IS TURNED ON

                                      SEQ_DELIVER (booster), since both pass isAC=true
  Line 1231 (SEQ_MIX)             -- Direct pcfOn(OUT_INVERTER); pcfOn(OUT_MIXER); -- mixer stage

  Line 879 (EXERCISE handler)     -- Bare pump-exercise path: pcfOn(OUT_INVERTER); pcfOn(bit); --

6. IS THE INVERTER USED DURING EACH STAGE?
  Fill/Transfer (SEQ_FILL)        Yes -- via stageBegin(OUT_TRANSFER, true, ...)
  Dose (SEQ_DOSE)                 No -- EXPLICITLY TURNED OFF at entry (DC dosing pumps)
  Mix (SEQ_MIX)                   Yes -- turned back on directly
  Deliver/Booster (SEQ_DELIVER)   Yes -- via stageBegin(OUT_BOOSTER, true, ...)
  Flush Fill / Flush Deliver      Yes -- both reuse stageBegin() with isAC=true (same
                                   transfer/booster relays)
  Pump tests (RUN_PUMP_TEST/EXERCISE)  Yes -- explicit pcfOn(OUT_INVERTER) before the test pump
  Testing (LCD dead-man combos)   Yes -- explicitly listed in the combo arrays
  Force Run                       Yes, IDENTICALLY TO A SCHEDULED RUN -- Force Run does not have
                                   its own inverter logic; it populates the same work-order fields
                                   ESP1 hands to ESP2's startWorkOrder(), which runs the exact same
                                   SEQ_FILL -> ... -> SEQ_DELIVER state machine traced above. There
                                   is no separate "Force Run inverter sequence" in the firmware --
                                   confirmed by the absence of any inverter-related code inside the
                                   Force-Run-specific parts of either ESP1 or ESP2.

7. EXACT INVERTER WARM-UP SEQUENCE
Generic, for any AC stage (stageBegin()/stagePoll(), ESP2/src/main.cpp:1019-1027, 1042-1047):
  1. stageBegin() sets sgPumpOn=false, sgT0=millis(), and if isAC, calls pcfOn(OUT_INVERTER) --
     inverter energizes immediately, pump does NOT.
  2. stagePoll()'s first branch: if (!sgPumpOn) { if (millis()-sgT0 >= (sgIsAC ?
     INVERTER_WARMUP_MS : VALVE_SWITCH_MS)) { attachFlow(sgFlow); pcfOn(sgPump); sgPumpOn=true;
     sgT0=millis(); } return 0; } -- the pump relay only energizes after the full warmup elapses.
This is identical for the transfer pump (SEQ_FILL) and booster pump (SEQ_DELIVER) -- both wait the
same fixed delay after their own stage begins, regardless of whether the inverter was already on
from a prior stage.

9. CAN FIRMWARE COMMAND THE INVERTER OFF BETWEEN TRANSFER AND BOOSTER?
THE CAPABILITY EXISTS (pcfOff(OUT_INVERTER) is a real, working function, used in several places
above) BUT IT IS NOT EXERCISED AT THAT SPECIFIC TRANSITION FOR A PLAIN IRRIGATION RUN. Traced
precisely: SEQ_FILL's completion (line 1182) calls endMeteredStage() (which calls stageEnd() ->
pcfOff(sgPump), i.e. the TRANSFER PUMP, not the inverter) and then explicitly
pcfOff(OUT_RES_VALVE), then goStep(wo.fertigate ? SEQ_DOSE : SEQ_DELIVER). For an IRRIGATION-ONLY
run (the common case, and what "Transfer alone"/"Booster alone"/"Full Force Run" tests would most
likely exercise), this goes straight to SEQ_DELIVER -- THE INVERTER IS NEVER TURNED OFF IN BETWEEN;
IT STAYS CONTINUOUSLY ENERGIZED FROM THE START OF FILL THROUGH THE END OF DELIVER. Only for a
FERTIGATION run does the inverter get toggled off (at SEQ_DOSE entry) and back on (at SEQ_MIX
entry) before reaching Deliver -- and even then, that's the dosing stage's requirement (DC pumps),
not something tied to the transfer-to-booster transition itself.

10. COULD FIRMWARE LEAVE THE INVERTER ON UNEXPECTEDLY?
No firmware path was found that fails to eventually turn the inverter off: every terminal state --
finishOk(), holdFault() (any fault including PWR_FAIL), emergency stop, and the boot-time safety
init -- routes through stopAll(), which unconditionally sets every bit including the inverter to
OFF alongside dropping the master cutoff (P17). No inverter-on code path was found that lacks a
corresponding off path. (This addresses the FIRMWARE'S OWN behavior only -- see the explicit
hardware caveat below for what firmware cannot see or control.)


DIRECT ANSWERS TO THE REPORT'S NUMBERED ITEMS
==============================================

1. CONFIRMED BY FIRMWARE: OUT_INVERTER = PCF8575 bit 5, active-low, with a complete, traced set of
   ON/OFF sites (all above) and no path that leaves it stuck on.
2. CONFIRMED BY FIRMWARE: Force Run's inverter behavior is identical to a scheduled run -- no
   separate logic exists.
3. CONFIRMED BY FIRMWARE: transfer and booster remain strictly sequential -- this investigation
   found nothing that changes the sequential-pump conclusion from the prior Force Run trace.
   sgPump/step remain single-valued; the inverter being continuously on across both stages does not
   imply the PUMPS overlap -- only one of OUT_TRANSFER/OUT_BOOSTER is ever the active sgPump at a
   time, per the previously-traced state machine.
4. CONFIRMED BY FIRMWARE, IMPORTANT NUANCE: the inverter is NOT commanded off between transfer and
   booster in the common (irrigation-only) case -- it stays on continuously across both. This is a
   normal, intentional design (both stages need AC power back-to-back), not a bug -- but it is
   directly relevant to the hardware hypothesis below.

   interacts with ESP2's P5 relay in a way that affects the voltage PZEM measures cannot be

   sgPumpOn && sgIsAC (ESP2/src/main.cpp:189, checked every 500ms). This check is agnostic to WHY
   the voltage is out of range -- it would fire identically whether the cause is a weak inverter,
   mains sag under pump inrush, or an unusual interaction between a manual switch and the relay.
   THE FIRMWARE CANNOT DISTINGUISH THESE FROM EACH OTHER; ONLY PHYSICAL MEASUREMENT CAN.
