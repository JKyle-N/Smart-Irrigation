====================================================================
1. ROOT CAUSE — pending-user control exposure
====================================================================
`isApprovedUser()` (script.js) already correctly returned false for pending/restricted/rejected/
disabled accounts, and `queueCommand()`/`writeZoneProfile()`/`writeManualHold()` already correctly
rejected their writes server-side-equivalently. The gap was entirely in the UI layer: `renderZonesUI()`
rendered the FULL "Firmware settings" editing block (quick-action buttons, dropdowns, N/P/K/pH
inputs, preset selector, Send to ESP1) unconditionally for every account, regardless of
`isApprovedUser()`. A pending user saw every control fully rendered and clickable; clicking any of
them queued a real Firebase write that `queueCommand()` then rejected after the fact with an error
message — exactly the "clickable button simply expected to fail" pattern the spec prohibits.

The System tab (`data-view="system"`) and Manual/Test tab (`data-view="manualtest"`) had an
analogous but distinct gap: neither tab was gated at all — not even by `isApprovedUser()`, let alone
by operator status. Any signed-in user, including pending, could open either tab and see every
control (Set Clock/Thresholds/Restore Defaults; Pump Exercise/Timed Pulses/Testing).


====================================================================
2. ROOT CAUSE — restricted-user control exposure
====================================================================
Identical root cause to #1. `isApprovedUser()` treats "restricted" and "pending" identically (both
evaluate to `false`), so every gap above applied equally to both statuses. No separate code path
existed for "restricted" specifically — which is exactly why the fix for #1 also fixes this without
needing a second mechanism.

3. FINAL ACCESS MODEL
====================================================================
No new role system was created. Two existing, orthogonal boolean checks now drive 100% of the
gating, exactly matching the spec's four-tier-plus-blocked model:

  isOperator()      -- auth.currentUser.uid is one of the two fixed OPERATOR_UIDS (main + creator/
                       backup). Already existed, unchanged. Gates: User Management (existing),
                       System tab (new), Manual/Test tab (new), and now specific commands
                       (RUN_PUMP_TEST, SET_EXERCISE, TEST_PULSE, the Manual/Test flow sweep,
                       SET_CLOCK, SET_THRESH, RESTORE_DEFAULTS) via a new `operatorOnly` option on
                       queueCommand().
  isApprovedUser()  -- isOperator() || myAccountStatus === "approved". Already existed, unchanged.
                       Gates: Zone Profile editing, Force Run, Cancel Force, Reboot, general Controls,
                       Diagnostics sweep, Emergency Stop/Recovery, and (unchanged) every other command.

  PENDING / RESTRICTED  = !isApprovedUser()  -> read-only (identical treatment, by design)
  NORMAL APPROVED       = isApprovedUser() && !isOperator()
  MAIN / CREATOR        = isOperator()  (implies isApprovedUser() too)
  BLOCKED (status "disabled") = pre-existing full-screen #blockedScreen takeover, unchanged, sees
                       nothing else on the page at all.

This is precisely PART 20's "capability model" mapped onto the existing data model with zero new
Firebase fields, zero new UID lists, zero new role framework.

8. EXACT UI GATING CHANGES (script.js)
====================================================================
1. `refreshOperatorUI()` extended: now also toggles `#systemTab`/`#manualtestTab` hidden based on
   `isOperator()`, and redirects to the dashboard tab if the user is currently on either view and
   loses operator status (same click-the-dashboard-tab pattern already used for `#usersTab`).
2. `queueCommand(type, payload, options)` gained a new `options.operatorOnly` flag, checked
   immediately after the existing `isApprovedUser()` check: `if (options.operatorOnly && !isOperator())`
   rejects with "This control is limited to the main/creator operator account." Applied to exactly
   the 6 command types that are Manual/Test- or System-exclusive: RUN_PUMP_TEST (all 3 buttons),
   SET_EXERCISE, TEST_PULSE, the Manual/Test tab's flow-sweep DIAG_SWEEP call (NOT the Diagnostics
   tab's own sweep, which sends the identical command type but must stay Normal-Operator-accessible
   -- these are the same command type from two different UI surfaces, so this distinction can only
   ever be enforced client-side, never by the Firebase rules), SET_CLOCK, SET_THRESH,
   RESTORE_DEFAULTS.
3. `writeManualHold(want)` gained an operator check on the ACQUIRE path only:
   `if (want && !isOperator()) return Promise.resolve(false);` -- releasing a hold (want=false) stays
   available regardless of role, since that direction only ever hands control back to automation and
   must never be blocked by a permission check.
4. `renderZonesUI()` restructured to branch on `const canEdit = isApprovedUser()` computed once per
   render: the sensor-reading matrix-grid and the live "Current configuration" summary paragraph are
   identical in both variants; the crop/growth-stage selectors become plain read-only text (no
   `<select>`, no change listener, no `writeZoneProfile()` trigger) when `!canEdit`; the entire
   "Firmware settings" block (quick-action buttons, mode/enabled/schedule dropdowns, window inputs,
   N/P/K/pH inputs, preset selector, Fill-from-crop and Send-to-ESP1 buttons) is replaced by a
   3-line read-only block (heading, the `#cfgCurrent` summary, and an explicit "Read-only access —
   editing firmware settings requires operator approval." notice) when `!canEdit`. All the editing
   wiring (event listeners, option population, form-state restore, window-visibility toggling) is
   now inside `if (canEdit) { ... }`.
5. New `lastZoneEditCapability` + `syncZoneEditCapability()` (declared next to `isApprovedUser()`):
   tracks the last-rendered edit capability and calls `renderZonesUI()` only on an actual flip, so
   Zone Profiles updates live when an operator approves/restricts/blocks the account mid-session
   without re-rendering on every routine 15s/live-data tick. Wired into both branches of
   `attachUserStatusListener()`'s status callback, and reset to `undefined` on sign-out (in
   `onAuthStateChanged`'s `!user` branch) so a fresh sign-in always re-evaluates rather than skipping
   a render because the boolean happens to match a previous session's value.

18. DIRECT-NAVIGATION PROTECTION
====================================================================
Audited the app's actual navigation mechanism: there is no hash-routing, no query-parameter routing,
and no other JS-driven view-switching path besides the single delegated click handler on
`document.querySelectorAll(".tab")`, which toggles `.active` on the clicked tab and the matching
`.view` section by `data-view`/`id` match. There is no alternate "reveal a view" entry point in this
codebase to protect against -- the ONLY way to make a hidden tab visible or force a view active
without going through that one click handler is direct DOM manipulation via browser devtools, which
no client-side JavaScript can prevent for a technical user with access to their own browser. This is
stated plainly rather than glossed over, per the spec's explicit instruction not to claim security
that isn't real: hiding the tab is a UI convenience only. What actually stops an unauthorized action
even if the view is forced visible is that every command the newly-visible view could send is
independently checked by `queueCommand()`'s `isApprovedUser()`/`operatorOnly` gates (or
`writeManualHold()`'s own `isOperator()` check), which do not care whether the view is visible --
confirmed by tracing every command path in #8/#19 below. Likewise for Zone Profiles: forcing the
read-only variant's container to somehow contain edit controls would require injecting new DOM
nodes with devtools (this codebase offers no code path that would do it), and even then
`quickSetColumnMode()`/`submitColumnConfig()`/`writeZoneProfile()` all still funnel through the same
`isApprovedUser()`-gated functions.

20. FIREBASE RULES STATUS -- FLAGGED CONFLICT, NOT SILENTLY FIXED (per the Final Stop Condition)
====================================================================
firebase-rules.json was inspected but NOT modified this pass. Here is the conflict the Final Stop
Condition asked to be surfaced rather than silently resolved:

The six `operatorOnly` command types added in #8.2 (RUN_PUMP_TEST, SET_EXERCISE, TEST_PULSE,
SET_CLOCK, SET_THRESH, RESTORE_DEFAULTS) are currently authorized at the Firebase-rules level for
ANY approved account -- the rules' `commands/$commandId/type` whitelist and the general
`isApprovedUser()`-equivalent write condition do not distinguish operator from normal-approved for
these types (or for any type). This means: the UI hides these controls from a normal-approved
account, and `queueCommand()`'s new client-side check refuses them too -- but a normal-approved
(non-operator) account with real Firebase Auth credentials could, with enough technical effort
(opening their browser's devtools and calling the Firebase SDK directly, bypassing this page's own
JavaScript entirely), still successfully queue one of these six command types, because the RULES
would still accept it.

This is a genuine gap between "hidden and client-refused" and "provably enforced server-side" for
these six command types specifically -- everything else in the access matrix (Zone Profile edits,
Force Run, Reboot, etc.) was ALREADY correctly rules-enforced at the approved/non-approved boundary
before this pass, and remains so. Per PART 17 ("only change rules if technically necessary") and the
Final Stop Condition, I did not attempt to close this by tightening firebase-rules.json myself this
pass -- that would mean adding operator-UID checks to specific command types in a ruleset that has
already caused one live regression this session (the RUN_PUMP_TEST whitelist omission), and is a
distinct decision from "make the UI honest," which is what was unambiguously specified.

**Smallest safe solution, if you want this closed at the rules level too**: add an explicit
`auth.uid === 'KaiqrwlOHeVdebbokPxZfcFLZiu2' || auth.uid === 'C8V39t4EDgUgjOt9GA6OeMukMsw2'`
condition to the `type` (or a new nested) validator specifically for these six command name
literals, leaving every other command type's existing approved-only rule untouched. This is a small,
scoped change, but it is still a live-production-rules edit and deserves your explicit go-ahead
given today's earlier near-miss, so I'm asking rather than doing it.
