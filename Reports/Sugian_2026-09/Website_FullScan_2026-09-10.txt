1. [FIXED] Temp-access grant used the browser's clock instead of Firebase's
--------------------------------------------------------------------------------
This is the PERMISSION_DENIED bug you hit granting 1h access -- already root-
caused and fixed earlier this session, included here for a complete record.
  Cause: grantTempAccess() computed `Date.now() + 1 hour` using THIS machine's
  system clock, which is running ~18.5 hours behind real time (confirmed against
  an external HTTPS server's Date header). That landed the value ~17.5 hours in
  the past relative to Firebase's own (correct) server clock, which the rules'
  server-relative validate window correctly rejected -- for both operator
  accounts identically, since it's a machine-clock problem, not an account
  problem.
  Fix (script.js, grantTempAccess()): no longer trusts Date.now() at all. Writes
  Firebase's own ServerValue.TIMESTAMP sentinel first, reads back what the
  server actually resolved it to, then writes server_time + 1 hour from that.
  Both writes are anchored to Firebase's clock, so this cannot fail this way
  again regardless of any future operator's machine clock accuracy.
  Status: DONE. No Firebase rules change was needed (the rule was correct all
  along -- it was correctly rejecting a genuinely invalid value).
