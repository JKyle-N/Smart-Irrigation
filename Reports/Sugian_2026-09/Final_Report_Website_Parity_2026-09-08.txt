      already / armed/running." for 3 seconds, then automatically falls through to whatever

    - The reverse direction (a web request silently overwriting an LCD-armed run) was ALREADY
      prevented before this change -- the Firebase handler's existing

      it. Confirmed only one side needed the fix.
    - Nothing about forceTick()'s countdown/fire-time re-check, delay bounds, or the sequential

6. EXACT COLUMN A/B/C BEHAVIOUR + COLUMN SELECTION/ACTIVATION
--------------------------------------------------------------------
Exactly 3 physical columns exist in firmware, tagged A, B, C (ESP1/src/main.cpp:105,
const char COL_TAG[NUM_COLUMNS] = {'A','B','C'}; NUM_COLUMNS=3 at line 100). There is no firmware
concept of a 4th column, of renaming these, or of a website-only "active column" -- the website's
3 zone ids map one-to-one onto these exact 3 tags.

Column enabled/disabled default (ESP1/src/main.cpp:104):
  COLUMN_ENABLED[NUM_COLUMNS] = { true, true, false };   -- Columns A and B enabled, COLUMN C
  DISABLED by default today. This is a real firmware state, not a website concept.

"Selection for editing" vs. "enabled for operation" are kept distinct exactly as required: the
website's 3-cards-at-once layout (unchanged from before -- see the plan's design-decision note)
means "which column are you configuring" is simply "which card you are looking at/typing into" --
a pure UI navigation concept with no firmware counterpart and no effect on anything until you press
that card's own "Send to ESP1" button. "Enabled/disabled" is its own explicit field/dropdown inside
each card (cfgEnabled), completely separate from merely viewing or scrolling to a card. Sending a
card's form only ever affects that ONE column (col := that card's own A/B/C tag) -- there is no way
for editing one card to affect another column's real state.

Each of the 3 cards now ALSO shows a live "Current configuration: Enabled/Disabled -- MODE --
Schedule: ... -- Targets: ..." line, sourced from the new read-only telemetry (section 2g/8),
refreshed on every snapshot, completely independent of whatever is currently typed into that
card's edit form. This satisfies "see current status of each column" and "clearly see which
columns are active" without inventing a second, competing UI paradigm -- see the approved plan's
explicit design-decision note on why the existing simultaneous-3-cards layout was kept rather than
replaced with a single hide-others dropdown.
