# C. High issues

### C-H1. OLD firmware's FORCE_RUN gate gives one generic rejection reason for 7 different conditions
- Severity: High   Type: OLD-firmware compatibility issue (already fixed in dev tree, unflashed)
- File/Function: OLD ESP1/src/main.cpp, firebaseCommandTick(), lines 5934-5938
- Evidence:
  if (sysState != IDLE_STATE || uiMode != UI_DATA || wo.active || pendingRun.active ||
      pendingExercise.active || esp2Held || fbRemoteExerciseId[0]) {
    firebaseQueueStatus(c.id, "rejected", "system is not safely idle");
    logEvent("FIREBASE", "REJECT", "FORCE|NOT_IDLE"); continue;
  }
  Compare dev tree (ESP1/src/main.cpp:6152-6166, confirmed present and unchanged this pass):
  identical condition list plus actuationsDisabled || webManualHeld(), and a "why" ternary
  giving one of six specific, distinct rejection strings instead of one generic one.
- What happens now: every FORCE_RUN rejected for any of 7 reasons on the physical rig shows
  literally the same words, "system is not safely idle" — indistinguishable whether the cause is a
  stuck run, a held fault, a running test, or the LCD being in a menu.
- Why it happens: the dev tree's own comment (line 6155-6157) confirms this was a deliberate,
  already-identified fix — the diagnosability gap was known and closed in the code that has not yet
  reached hardware.
- What should happen: the specific reason should reach the dashboard, as it already does in the
  dev tree.
- Recommended fix: flash the dev-tree ESP1 firmware (not done — outside this audit's scope).
- Requires: New firmware (ESP1). CONFIDENCE: HIGH (both trees read fresh, word-for-word diff).

### C-H2. OLD firmware's FORCE_RUN gate is missing the actuationsDisabled/webManualHeld() checks
- Severity: High   Type: OLD-firmware compatibility issue (already fixed in dev tree, unflashed)
- File/Function: same location as C-H1.
- Evidence: the OLD condition list (quoted above) has no actuationsDisabled/webManualHeld()
  terms at all. The dev tree's own comment states plainly why they were added: "forceTick()/
  sendForceWorkOrder() both re-check them at fire time so no work order is actually sent while
  locked out, but without this the dashboard was told 'accepted, armed' for the full countdown (up
  to 300s) before silently failing — directly contradicting the disabled-actuations banner's own
  claim that forced runs are blocked immediately."
- What happens now on the physical rig: submitting a FORCE_RUN while actuations are disabled,
  or while another session has Manual/Test open holding the rig, is accepted and armed (a
  countdown is shown), then silently aborts (via forceAbort()) once the countdown expires — never
  actually running anything, but also never telling the operator immediately that it wouldn't.
- Why it happens: the arm-time gate on OLD firmware doesn't check these two conditions; only
  the separate fire-time re-check inside forceTick() (which the OLD firmware still has,
  unverified this pass but structurally present per the surrounding code) actually stops it from
  physically running.
- Is hardware safety actually bypassed? No — per the dev tree's own comment, the fire-time
  re-check is a pre-existing, separate safeguard that both trees share; this finding is about
  dashboard honesty, not physical safety.
- Recommended fix: flash the dev-tree ESP1 firmware.
- Requires: New firmware (ESP1). CONFIDENCE: HIGH.

# R. Manual/Test findings

- OLD firmware: long webManualSeq (ESP1/src/main.cpp:993), long seq = doc["seq"] | -1
  (:5713) — 32-bit.
- Dev firmware: int64_t webManualSeq, int64_t seq = doc["seq"] | (int64_t)-1 — 64-bit.
- Why it matters: the website sends seq: Date.now() (~1.7e12), which does not fit a 32-bit
  long. ArduinoJson's | operator returns the literal default (-1) on a type mismatch rather
  than truncating — so on the OLD firmware, seq reads back as -1 on every single poll,
  seq != webManualSeq never becomes newly true after the first poll, webManualPing never gets
  set again, and webManualTick() never re-evaluates a fresh request.
- Practical consequence on the physical rig today: Manual/Test's "Proceed" button cannot
  reliably light up — the hold is effectively non-functional on the currently-flashed hardware,
  independent of anything the website does correctly.
- Sequence overflow/truncation: confirmed — this is the truncation bug, not a separate one.
- Tab-switch/refresh/stale markers: the website-side kick/session logic (already audited and
  fixed earlier this engagement) is unaffected by this — this is purely an ESP1-side numeric-type
  bug independent of the website's own correctness.
- CONFIDENCE: HIGH (both trees read fresh, this pass and the prior one).

# Z. Root-cause opinion on FLOW_FAIL / SOIL_MISSING, and what was fixed for them

You asked directly what I think caused the two live faults, and whether I can fix them. Short
answer: both are almost certainly real physical conditions, not code bugs — the OLD and dev firmware
are byte-identical on every code path involved (see Sections O and P), which rules out a
version-mismatch or logic-bug explanation. I can't reach into a valve, a pump, or a soil probe from
here, so I can't fix the physical cause itself. What I found and fixed instead:

CORRECTION to this report's Section O: I originally wrote that the flow sensor's exact pulse count
at the moment of the fault was "only visible in the SD log/serial monitor, not the dashboard." That
was wrong. Tracing the full path (ESP2's holdFault(), ESP1/src/main.cpp:1090-1104 dev tree) shows
ESP2 already appends the pulse count to the fault message it sends ESP1
(reply(...+"|pulses="+String(fp))), ESP1's handleEsp2Response() passes that whole string through
unmodified as `loc`, and enterFaultHold() folds it into lastFaultMsg — which IS what the live
dashboard's fault banner title reads from. So on the CURRENTLY FLASHED hardware, right now, with NO
code change: open the fault banner and read the exact fault text. If it reads
"FLOW_FAIL TRANSFER|pulses=0 COL_x", zero pulses were counted at all — most consistent with a dead
transfer pump, a valve that never opened, or a disconnected flow sensor. If it reads pulses=<some
number greater than 0>, flow started and then stopped — more consistent with an air lock or a
weakening pump. This was already designed into the firmware (the code comments call it out as
"diagnostic C-3") — I had simply not traced it far enough the first time.

New fix (dev tree only, needs a reflash) — SOIL_MISSING did NOT have the equivalent enrichment: the
fault message only ever said e.g. "SOIL_MISSING COL_B", not which of the two ways a column can break,
nor the raw sensor values. I added it (ESP1/src/main.cpp, the SOIL packet handler,
~line 2314-2325 dev tree), following the exact same pattern already used for FLOW_FAIL's pulse count:
the fault now reads e.g. "SOIL_MISSING COL_B|PROBE_DIVERGE|raw=707,391" (the two probes disagree
beyond tolerance, NPK is covering the reading) or "SOIL_MISSING COL_B|NO_READING|raw=-1,-1" (both
probes reported nothing at all) — pointing at a different physical check each time. This is a
firmware change, so it needs a reflash before it applies to the live fault reporting.

New website fix (source only, needs publishing) — Website/script.js: added explainFaultCode(), which
decodes both the FLOW_FAIL pulse count and the new SOIL_MISSING detail into a plain-language
sentence, and wired it into the fault banner (for a currently-held fault) and the Diagnostics tab's
"Last fault" row (for a Major alert like SOIL_MISSING that never raises the banner). Once published,
this will read the pulses=N value that's ALREADY being sent by the currently-flashed firmware today
(no reflash needed for the FLOW_FAIL half of this); the SOIL_MISSING half only has something to
decode once ESP1 is eventually reflashed with the enrichment above.

What I still can't tell you without physical inspection: which specific one of (dead transfer pump /
stuck reservoir valve / air-locked suction line / dead flow sensor) is true for the flow fault, or
whether Column B's probes are wired loose, corroded, or genuinely failed — those need hands on the
rig. The pulse count and raw soil values narrow it considerably; they don't replace looking at it.
