1. [FIXED] queueCommand()'s new activity-logging line could report a false
   "Could not queue command" failure
--------------------------------------------------------------------------------
The Recent-Activity feature added this line inside queueCommand()'s success
callback:
    db.ref(`activity/${auth.currentUser.uid}`).push({...})
If the user signs out in the brief window between the command push starting
and this callback running, auth.currentUser is null there, and .uid throws
SYNCHRONOUSLY inside the .then() -- which the chain's own .catch() then reports
to the user as "Could not queue command: ...", even though the real command had
ALREADY succeeded moments earlier. Narrow (needs a sign-out mid-flight) but a
real, misleading-failure-message bug.
Fix: capture `const myUid = auth.currentUser?.uid;` first and skip the activity
write entirely if it's null, instead of letting a null access blow up the whole
callback.

2. [FIXED] Deleting a user left /presence/{uid} and /activity/{uid} behind
   forever
--------------------------------------------------------------------------------
delete-user-api's delete-user.js only ever removed /users/{uid} after deleting
the Auth account. /presence/{uid} and /activity/{uid} (both added this session)
are SEPARATE top-level nodes, not children of /users, so they were silently
orphaned on every delete. Harmless as dead data (neither is ever displayed
again once the uid drops out of /users, which is what every reader keys off),
but cleaned up anyway now that this call already holds the Admin SDK's
rules-bypassing access to do it properly in the same trusted operation.
Fix: the delete now removes /users/{uid}, /presence/{uid}, and /activity/{uid}
together via Promise.all(). NOT YET DEPLOYED -- this project is served via
`vercel --prod` from a local, non-git-tracked folder (confirmed via
.vercel/project.json), so it needs an explicit Vercel deploy, separate from the
website publish and the Firebase rules deploy. Ask before running it.

3. [FIXED] README.md's RTDB node-layout table had drifted out of sync
--------------------------------------------------------------------------------
Missing entirely: presence/$uid, activity/$uid, and users/$uid's
tempAccessUntil/subOperator fields (all added this session, never documented).
Also a factual error: claimed testHold's `bit` whitelist has 9 targets: it
actually has 10 (transfer/colA/colB/colC/mixer/nutA/nutB/nutC/phUp/phDn) --
recounted directly against both the rule text and index.html's dropdown.
Also corrected a stale claim that the Proceed button "stays disabled" without
the manual rule -- no longer true since the 2026-09-10 Proceed-gate revision
(it now reveals the panel independent of ESP1/the manual hold's state; the
individual test buttons are the actual freshness gate).
Fix: table entries added for presence/activity/users' two grant fields, target
count corrected, Proceed-button claim updated to match current behaviour.
