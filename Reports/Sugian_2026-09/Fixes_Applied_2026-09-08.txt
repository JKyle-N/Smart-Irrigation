[1] CRITICAL — ESP2: EXERCISE / PRIME_START overcurrent protection gap
====================================================================
File: ESP2/src/main.cpp
safetyMonitor() now also activates while an EXERCISE pump run (`exRunOffAt != 0`) or an AC
PRIME_START line (`primeLine != "" && primeIsAC`) is active, not only during a work-order stage.
A new `auxPowerFaultStop()` helper picks the correct teardown for whichever context tripped: a
work-order stage still goes through the existing holdFault()/RESUME machinery; EXERCISE/Prime abort
the actuator immediately (mirroring their own normal-completion teardown) and report `PWR_FAIL,...`
directly, since there's no tank/work-order state for an operator to RESUME in those cases.
Net effect: an unattended EXERCISE run or a PRIME purge on a faulted pump now gets the same PZEM
overcurrent/voltage/no-current protection a scheduled fertigation run already had.

[2] HIGH — ESP1: cross-core Firebase-auth String race
====================================================================
File: ESP1/src/main.cpp
Extended the same netMux lock/copy-then-use pattern already used at the FBASE,STATUS SMS handler
to the remaining unguarded core-0 read sites:
  - fbBuildUrl() -- copies fbIdToken under netMux before building the URL.
  - fbEnsureToken() -- copies fbIdToken under netMux for its top-of-function validity check.
  - firebaseUploadLive() -- fbIdToken/fbAuthErr now copied under the same lock block that already
    covered fbUrl/firebaseEnabled/credsCfg/etc., instead of being read bare later in the function.
  - portalAdminHtml() -- fbUrl/fbApiKey/fbEmail/fbPassword/fbRefresh/fbAuthErr/fbUid all copied
    under one netMux block at the top of the Firebase section, all subsequent reads in that render
    path use the local copies.
No behavior change for a normal user; closes the heap-corruption/crash window against a
FBASE,SIGNOUT SMS arriving mid-render or mid-request on core 0.

[3] MAJOR — ESP2: readMixerCurrent() single-sample AC read
====================================================================
File: ESP2/src/main.cpp
Replaced the single instantaneous analogRead() with a small non-blocking ring buffer (24 samples,
one new sample per call -- no busy-wait, no delay(), keeps the file's "non-blocking everywhere"
rule) reporting an RMS magnitude across the most recent samples. At normal loop() cadence this
converges to a real RMS reading within a handful of calls. `resetMixerCurrentRing()` is called when
SEQ_MIX starts so a new mix run doesn't inherit stale samples from a previous one.
Net effect: the end-of-mix no-load check and the real-time overcurrent trip no longer depend on
which point of the AC sine wave a single sample happened to land on.

[5] MEDIUM — Firebase rules: command writes had no shape/bounds validation
====================================================================
File: Website/firebase-rules.json (same manual-publish step as [4] applies)
Added a `.validate` on `type` restricting it to the 16 command names in script.js's own documented
"dashboard contract" (FORCE_RUN, EMERGENCY_STOP, RECOVER, ESTOP_RECOVER, ENABLE_ACTUATIONS,
DISABLE_ACTUATIONS, CANCEL_FORCE, ACK_FAULT, SET_COLUMN, SET_EXERCISE, REBOOT, TEST_PULSE,
DIAG_SWEEP, SET_CLOCK, SET_THRESH, RESTORE_DEFAULTS). Added narrow range `.validate` rules on the
unambiguous numeric payload fields the client already clamps: `liters` (0-20), `delaySeconds`
(0-300), `targetN/targetP/targetK` (0-2000), `targetPH` (3-9). Each is a no-op when the field is
absent, so command types that don't carry it are unaffected.

Deliberately NOT validated at the rules level: `col`/`mode`/`enabled`/`schedMode`/`preset`/
`doseMl`/`columns`/window fields -- their valid shape depends on which command type carries them,
and getting a nested per-type rule wrong risks silently breaking a legitimate command with no
obvious symptom other than "it stopped working." ESP1 already validates all of these fully before
acting (confirmed in this session's earlier website/LCD-parity audit), so this was judged a
reasonable place to stop for a rules-level, defense-in-depth pass rather than attempting a full
schema.

[6] MEDIUM — Website: renderZonesUI() wiped unsaved form edits on any zone-config change
====================================================================
File: Website/script.js
Added `captureZoneFormState()` (reads the current value of every zone's Firmware-settings form
field: cfgMode/cfgEnabled/cfgSched/cfgWinStart/cfgWinEnd/cfgN/cfgP/cfgK/cfgPH/cfgPreset) called at
the top of renderZonesUI() before the `container.innerHTML = ""` teardown, and
`restoreZoneFormState()` called for each zone right after its inputs are rebuilt. A remote or local
zonesRef change (e.g. changing zone A's crop dropdown) no longer discards what an operator was
mid-typing into zone B or C's (or A's own) not-yet-sent detailed form.
Does not persist across a full page reload -- only across the live re-renders this listener causes,
which is what the finding was actually about.

[8] MINOR — ESP1: dead calBattI / current-channel NVS calibration path removed
====================================================================
File: ESP1/src/main.cpp
Removed `calBattI` (the unused current-channel opto-ADC polynomial), the `battICalLoaded` flag, the
NVS "i" blob load in loadBattCal(), and the `analogSetPinAttenuation(PIN_BATT_I, ...)` setup call --
all dead code, since battery current has come entirely from the ACS758-via-ADS1115 I2C path
(unaffected, not touched) since that migration. `battCalLoaded` now reflects only `battVCalLoaded`
(voltage), which is the only channel this NVS blob ever actually affected in practice. A pre-
existing "i" NVS blob from an older firmware/bench-tool run is simply ignored now -- same net effect
as before (it was never applied to anything), just without the misleading "loaded from NVS" success
report for a calibration that did nothing.

This is separate from, and does not touch, the battery-telemetry PUBLISH fix from earlier today
(the `battVCalLoaded`/`acsOk_`-gated publish logic in firebaseUploadLive() is unaffected).

[9] MINOR — ESP1: SET_CLOCK day-of-month validation ignored month/leap-year
====================================================================
Files: ESP1/include/pure_math.h, ESP1/test/test_pure_math/test_pure_math.cpp, ESP1/src/main.cpp
Added `isLeapYear(year)` and `daysInMonth(year, month)` as pure, host-testable functions in
pure_math.h (Gregorian leap-year rule), with new unit tests (test_days_in_month_ordinary_year,
test_days_in_month_leap_year_rules, test_is_leap_year) registered in the native test suite -- see
the toolchain caveat above about running them in this environment.
Both SET_CLOCK validators now use it:
  - Firebase command handler: rejects c.clkD > daysInMonth(c.clkY, c.clkMo) instead of a flat > 31.
  - LCD Set Clock editor: re-clamps the day field to daysInMonth(year, month) whenever the year,
    month, OR day field is adjusted, so e.g. dialing the month to February automatically pulls an
    already-selected day 30/31 back down to 28/29 before it can be committed.

[12] LOW — Vercel: delete-user-api leaked Admin SDK error text to unauthenticated callers
====================================================================
File: delete-user-api/api/delete-user.js
Split the token-verification step into its own try/catch: a verifyIdToken() failure (invalid
signature, expired, garbage token, or no token at all) now logs the real error server-side only

function keep their existing detailed error responses, since that code path is only reachable after
the caller is already confirmed to be one of the two operator UIDs -- not an unauthenticated-facing
leak the way the token-verification branch was.
