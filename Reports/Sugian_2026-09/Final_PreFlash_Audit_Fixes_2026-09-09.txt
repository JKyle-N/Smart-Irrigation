2. ESP1 FIRMWARE — 4 fixes applied, built clean (0 errors/warnings, size unchanged from baseline)
====================================================================
1. `SET_THRESH` (Firebase command) now rejects a missing/negative `thGap` instead of silently
   defaulting it to 0 — previously a partial payload could silently make the system "fertigate on
   any positive shortfall at all" instead of only past a meaningful one, with no log/alert
   distinguishing it from a deliberate 0.
2. ThingSpeak upload (`tsUpload()`) now uses the same validity gates (`envValid`/`tankValid`/
   `lightValid`/`battVCalValid`/`acsOk_`) as the Firebase live snapshot already did — previously it
   published every field unconditionally, including a possibly-fabricated placeholder battery
   voltage/power before the sensor is ever calibrated. A field is now simply omitted from that
   update when its backing sensor isn't valid, matching Firebase's "absent, not fabricated" behavior.
3. SMS `WIFIPORTAL,STOP` is no longer case-sensitive — `WIFIPORTAL,stop` (lowercase) previously fell
   through and (re-)started the SoftAP portal instead of stopping it. Fixed the same way as
   yesterday's `WIFI,ON/OFF` case fix.
4. A per-column MANUAL schedule window with start >= end (e.g. accidentally configuring an overnight
   window) previously passed validation and then silently, permanently disabled that column with
   only a routine, non-alerting log line. Now rejected on the Firebase `SET_COLUMN` path, and
   auto-corrected in real time on the LCD editor (same live-correction approach as the day-of-month/
   leap-year fix from yesterday) so an invalid window can never be committed from either surface.

3. ESP2 FIRMWARE — 3 fixes applied, built clean (0 errors/warnings, size unchanged from baseline)
====================================================================
1. **MAJOR — closes the same safety gap yesterday's EXERCISE/PRIME fix was meant to close, in the
   one path it didn't reach.** `SEQ_MIX` (the mixing stage of every fertigation run) drives the
   mixer directly via `pcfOn()` without ever calling `stageBegin()`, so it was invisible to
   yesterday's widened `safetyMonitor()` gate exactly the same way EXERCISE/PRIME_START used to be —
   meaning every fertigation run's mix stage (up to several minutes) ran with zero PZEM AC
   voltage-window/overcurrent/stall protection; only a mixer-specific overcurrent check that never
   watches supply voltage at all. Fixed by adding a `mixActive` context to `safetyMonitor()`'s gate,
   with its own fault-teardown branch (turns off the mixer, holds the fault) mirroring the pattern
   already used for the existing mixer-overcurrent fault right next to it.
2. **MAJOR — closes a genuine simultaneous-actuation possibility.** `EXERCISE` (ESP1's own
   unattended, automatic 2-day preventive-maintenance pump run) could previously start concurrently
   with an active `PRIME_START` purge, `CAL_START` calibration stream, or a dispatched work order —
   each of those three already correctly refused each other, but none of them checked whether an
   EXERCISE run was in progress, and EXERCISE itself didn't check them either. This could have
   energized two actuators at once, against the project's locked sequential-never-simultaneous pump
   architecture. Fixed by adding the missing mutual-exclusion checks on both sides.
3. **MINOR** — a `PWR_FAIL` (or other non-flow fault) occurring while already running a flow-blind
   recovery no longer erases the "flow sensor is known dead" memory; it's preserved across that fault
   instead of being clobbered back to false, avoiding one unnecessary extra operator RESUME cycle in
   an already-rare double-fault scenario.

**Nano: no changes.** Confirmed clean by the fresh scan — sensor-hub-only design fully intact.
